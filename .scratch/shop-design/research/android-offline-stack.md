Those are existing human decisions, not choices made by this research. Product templates are independent copies, and the catalog does not require a part-maker-brand lookup; follow [catalog decisions](../issues/02-dynamic-catalog.md) and the repository glossary.

Use Room as the local source of truth and keep UI, application operations, scanner/resolver, QR renderer, printer transport and backup service separate. Business transactions must advance the durable shop revision; a backup job captures a consistent revision and attachment set, then acknowledges only that revision after a complete restore point is published. Acknowledging an older revision must leave newer writes pending. Keep the record-outbox discussion below only as a generic capability alternative, not the selected architecture. See [source verification](android-offline-source-verification.md) for the refreshed authoritative evidence.

## Scope and conclusion

For one active device, an appropriate candidate is Compose UI → ViewModel → application operations/repositories → Room/SQLite, with bundled ML Kit barcode scanning fed by CameraX, local ZXing QR encoding, a print adapter boundary, and durable local backup jobs scheduled by WorkManager. All catalog, cart, stock and cash-sale operations should commit locally; neither a network connection nor a background scheduler belongs in their success condition. A shared QR resolves a stocked product; quantity is entered by the cashier, as already confirmed by the user. The scanner must not treat one decode as a serialized physical unit.

This recommendation follows Android's local-source-of-truth architecture and local-first queued-write guidance. Shop policies come from the linked decision tickets. [Android offline-first guidance](https://developer.android.com/topic/architecture/data-layer/offline-first?hl=en).

## Room, transactions and Compose observation

Room supports asynchronous one-shot DAO operations with `suspend` and observable reads with `Flow`. It prevents main-thread database access. Table invalidation can rerun a query even when the changed row does not affect its result; `distinctUntilChanged` can suppress equivalent result emissions. Thus catalog search, cart contents, low-stock counts and sync indicators can all observe local storage. [Room asynchronous queries](https://developer.android.com/training/data-storage/room/async-queries).

Compose should collect exposed screen state with `collectAsStateWithLifecycle`; Android documents that integration separately through `lifecycle-runtime-compose`. Screen recomposition and remembered UI state are not a durable cart store. Persist cart identity and lines in Room, and reconstruct UI after process recreation. [Compose state guidance](https://developer.android.com/develop/ui/compose/state).

Room's `@Transaction` runs a concrete DAO operation in one database transaction, committing unless an exception occurs. Individual generated inserts/updates/deletes are already transactional, but that does **not** combine an entire checkout. Relation reads can also require a transaction for a consistent multi-query result. [Room Transaction reference](https://developer.android.com/reference/androidx/room/Transaction).

**Recommended operation boundary:** checkout rereads and validates the cart and stock under the same local transaction, checks the cart has not already completed, creates the sale and historical line snapshots, records cash data and stock movements/balances, transitions the cart, and advances the shop revision/backup-dirty state. Failed validation must roll back the entire operation. Use a unique checkout/operation identifier so a double tap or recovered UI cannot create two sales. Atomicity alone does not decide reservation, shortage or price policy; follow the settled checkout ticket 04: no reservations, retained line quotes and explicit shortage correction. Do not hold a database transaction open while scanning, showing a dialog, calling a server or printing.

## Durable scheduling versus immediate operations

WorkManager stores scheduled work persistently and reschedules it across app restarts and device reboots. It supports named/unique work and constraints, making it suitable for reconnect-driven sync and recovery. That persistence is scheduler persistence, not a replacement for the business outbox or an exactly-once network contract. [WorkManager overview](https://developer.android.com/develop/background-work/background-tasks/persistent).

Requests can require network availability; all configured constraints must be met, and losing constraints can stop a worker. `Result.retry()` schedules a later attempt with linear or exponential backoff; the minimum backoff is ten seconds. Periodic work has a minimum fifteen-minute interval, and actual timing depends on constraints and system optimization. Expedited work has quotas and can be deferred. Therefore no exact reconnect time or immediate completion guarantee should appear in the design. [Work request constraints, retries and timing](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

**Original generic outbox alternative (design inference, superseded for this shop):** insert a stable operation ID, entity/type, local sequence/version, payload schema version, payload or reproducible snapshot, and pending state with the business mutation in one transaction. A worker sends bounded batches; acknowledge locally only after server acknowledgement. Resend the same ID after a lost response, with server deduplication/idempotency. Separate retryable transport errors from authentication or permanent validation problems needing attention. Persist last successful acknowledgement, pending count and actionable errors for UI. Reconcile pending work on app startup as well as enqueueing after commits, covering process death between DB commit and scheduler enqueue. Never replay a sale by deducting local stock a second time during upload.

A foreground “sync now” may invoke the same sync service while the app is active; durable pending records survive interruption. Core operations use immediate local coroutines and transactions. Backup and replacement policy are settled in ticket 05, but implementation and recovery validation remain outstanding; a successful scheduled job alone proves none of them. One active device removes the need to design distributed stock allocation, but retransmission safety still matters.

## Scanning and first-use offline behavior

| Option | Verified constraint | Consequence for this scope |
| --- | --- | --- |
| Bundled `com.google.mlkit:barcode-scanning` | Model statically linked with the app; immediately available | Preferred candidate for scanning on first launch without network |
| `com.google.android.gms:play-services-mlkit-barcode-scanning` | Model dynamically downloaded through Play services; requests before completion return no results | Install-time/requested download is preparation, not a guarantee for an unprepared offline installation |
| Google code scanner | UI delegated to Play services without the app requesting camera permission; scanner module is downloaded before use | Convenient UI, but downloaded-module prerequisite conflicts with unconditional first-use offline scanning |

The ML Kit setup guide currently specifies API 23 minimum; the starter's declared minSdk 33 exceeds it, without proving the shop device is supported. Prefer the explicit setup requirement over inconsistent generated summary text. Bundling only addresses the model dependency; camera access, permissions and label readability still need validation. [ML Kit Android scanning and installation options](https://developers.google.com/ml-kit/vision/barcode-scanning/android), [Google code scanner module lifecycle](https://developers.google.com/ml-kit/vision/barcode-scanning/code-scanner).

CameraX `ImageAnalysis` supplies frames to an analyzer and integrates with ML Kit. Bind camera work to the screen lifecycle; use an appropriate backpressure strategy and close each `ImageProxy` after asynchronous processing finishes so frames do not stall. [CameraX image analysis](https://developer.android.com/media/camera/camerax/analyze).

**Recommended scanner boundary:** return a decoded identifier and format to a resolver, not a stock mutation. Parse only the app's supported payload format, look up local records, reject unknown/deactivated IDs visibly, and provide manual search when camera permission is denied or a label is damaged. Suppress repeated frames from triggering repeated actions. A product scan can prefill template/product details or select a cart product according to the screen context; the resolved catalog model must determine which identity is encoded. No assumption is made about autofocus, flash, scan distance or external scanner hardware. Acceptance should include a clean install with networking disabled before the first scan, followed by realistic printed-label trials.

## QR generation and printing are separate capabilities

ZXing core provides `QRCodeWriter`, which converts a string to a `BitMatrix` locally, accepts QR error-correction and margin hints, and defaults to a four-module quiet zone. Its source carries Apache 2.0 licensing. Encoding needs no hosted QR service. Preserve quiet zones, crisp module boundaries and short stable identifiers in the label renderer. [ZXing QRCodeWriter source](https://raw.githubusercontent.com/zxing/zxing/master/core/src/main/java/com/google/zxing/qrcode/QRCodeWriter.java).

**Recommendation:** use a versioned app-owned product identifier payload, with a human-readable code/name beside the QR. Do not encode changing stock, price or entered quantity as authoritative label state. The shared label can identify the same stocked product for multiple loose pieces; a separate label/token scheme would be a catalog policy change. ZXing encoding does not establish physical readability or printer compatibility.

Android custom printing uses `PrintManager` plus a `PrintDocumentAdapter`; the adapter lays out and writes page content, as PDF, in response to print settings. This supports locally generated label sheets/documents. [Android custom document printing](https://developer.android.com/training/printing/custom-docs). Discovery and communication with actual printers belongs to a print service, so the existence of Android printing APIs does not prove that a chosen shop printer has a compatible installed service. [Android PrintService reference](https://developer.android.com/reference/android/printservice/PrintService).

For direct thermal/label output, keep a separate printer adapter for the manufacturer's documented SDK or command protocol. Epson's ESC/POS reference explicitly scopes supported models and warns that customized models can have different commands and parameter ranges; “Bluetooth printer” is a transport description, not a compatibility guarantee. [Epson ESC/POS reference](https://download4.epson.biz/sec_pubs/pos/reference_en/escpos/index.html). Android Bluetooth access additionally depends on declared/runtime permissions for the target OS; current APIs distinguish connecting and scanning. [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions).

For the selected TE244 USB/OTG integration, verify the actual printer firmware, connection (USB/Bluetooth/local network), supported language/service/SDK, paper/label dimensions, DPI, margins and status/acknowledgement behavior. Test offline printing, cancellation, reconnect and reprint. A PDF generated offline is feasible; physical printing offline remains conditional on the actual printer path. Printing failure must not roll back a completed cash sale; label/receipt generation and reprinting should use persisted data.

## Typed catalog data, money and quantity

Room entities map to tables and support primary keys and indices, including unique indices. Relationships should use explicit relational modeling rather than entity object references. [Room entities](https://developer.android.com/training/data-storage/room/defining-data), [Room relationship guidance](https://developer.android.com/training/data-storage/room/relationships).

**Original generic catalog alternatives (superseded by ticket 02 where different):** retain separate lookup tables/IDs for distinct concepts such as part-maker brand, motorcycle brand/model, unit and supplier. Store display labels plus a searchable normalized key; inline creation should create a local row atomically, then select its ID. Duplicate normalization and merge policy need human agreement. Model fitment as a relation where many-to-many is needed. The settled catalog excludes part-maker brands; do not add that generic lookup alternative to this shop. Keep product templates separate from stocked products and historical sale snapshots separate from mutable catalog fields.

For category/custom attributes, use an attribute definition (stable ID, category applicability, type, unit/lookup domain, requiredness and validation metadata) plus typed values linked to the owning template/product. Candidate value types include text, boolean, scaled decimal, date and lookup ID. Enforce the selected type and allowed range; avoid one untyped text column for values that must be filtered numerically. SQLite uses dynamic typing, and numeric affinity may coerce numeric-looking text, so application typing alone must not be mistaken for database enforcement. [SQLite datatypes and affinity](https://www.sqlite.org/datatype3.html). Foreign keys can enforce lookup references when configured; verify enforcement and migration behavior rather than assuming labels guarantee identity. [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html).

SQLite integers within signed 64-bit range are exact; REAL values use approximate binary floating point. SQLite arithmetic may promote integer overflow to floating point and integer division truncates, so INTEGER columns alone do not guarantee checked calculations. Validate arithmetic before persistence. [SQLite expression semantics](https://www.sqlite.org/lang_expr.html#operators). [SQLite numeric accuracy](https://www.sqlite.org/floatingpoint.html). **Original generic representation alternative (superseded by whole rupees/counts in ticket 08):** represent finalized INR amounts as checked `Long` minor units (paise) with explicit currency, and compute decimal inputs using exact decimal/scaled arithmetic rather than `Float`/`Double`. Represent quantity as checked integer base units or an integer plus fixed declared scale/unit, supporting piece counts and measured stock. Retain the scale/unit interpretation in sale snapshots. Validate bounds and intermediate multiplication overflow.

The original representation recommendation did not choose allowed unit families, fractional precision, piece divisibility, conversion factors, unit-price precision, line versus bill rounding, discounts, cash tender/change rules or negative-stock behavior. The resolved stock, checkout and schema tickets now determine the shop arithmetic contract. Do not silently round a measured quantity to pieces or truncate a sub-paise intermediate result. Keep the balance and stock-movement ledger in the same exact quantity representation and transactional boundary.
